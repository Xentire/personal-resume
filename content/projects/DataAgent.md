## 架构取舍对比

每个决策点都对应代码里的一个落点，不做「用了什么技术」的罗列。

| 决策点 | 备选方案 | 实际选择 | 依据与结果 |
| --- | --- | --- | --- |
| 编排范式 | ReAct：边想边调工具，步数不可预估 | Plan-and-Execute：17 节点分 4 段（理解 6 · 计划 4 · 执行 6 · 交付 1） | 长链路要的是路径与成本可控，发散无法验收；先出完整计划，才能给每一步单独挂校验预算 |
| 服务边界 | 单个 Java 服务内嵌全部编排逻辑 | Java 事实层（权限 / 数据 / SQL 执行）+ Python 决策层（编排 / 推理），C 通道 7 个能力接口 + HMAC 签名 | 权限与凭证必须留在 Java。Python 侧 65 个文件零直连数据库，靠 `check_boundary.py` 静态扫描守住；重构后 Java 侧净减 60 个文件，SQL 执行入口收敛为 1 个签名校验门面 |
| 模型接入 | Spring AI 的 ChatClient / Advisor 直连 | Java 只保留 EmbeddingModel / TextSplitter / VectorStore（向量侧），ChatClient 在重构中删掉 | Java 不再持有 LLM 调用，流式事件由 Python 侧 `astream_events` 产出、Java 只做转发；留一个没人调用的 `getChatClient()` 是最坏的选择 |
| 检索策略 | 纯向量召回 | 向量 + BM25 + RRF 融合（k=60） | 进向量的文本只有「表名/列名 + 注释」，采样值只进 metadata、不参与相似度；表名字段名这类精确词必须靠 BM25 补。TopK 命中率 61% → 79% |
| 质量兜底 | 只靠模型自省，错了再问一遍 | 三层自省（计划结构校验回退重规划 / SQL 多轮重试 / 语义层检测 SQL 与 Schema 冲突）+ 零 token 的纯函数机械校验 | 同比基期截断、缺失补零这两类错数在语义上都「说得通」，模型自省抓不到；SQL 一次通过率 74% → 91%（N=120 评测集） |
| 语义检查额度耗尽后 | 判失败终止 / 无限重试 | 判通过并继续执行，报告里如实写明该口径不可用 | 错的数据比没数据更危险，但无限重试比两者都糟。改三次还带着 `LAG(12)` 截窗口，就让它跑出来、把限制写进报告 |
| HITL 断点方式 | `interrupt_before` / 依赖 checkpoint 内部结构恢复 | Python 侧 `interrupt()`，Java 侧协议翻译与恢复 | 不把框架内部结构暴露成跨服务契约，升级 LangGraph 不必连带改 Java；执行前暂停确认、反馈后恢复或重新规划 |
| SQL 口径检查实现 | 正则匹配 / 引 AST 解析器 | 手写括号匹配 | `LAG(SUM(x), 12)` 这种嵌套聚合，正则找不到匹配的右括号，AST 又要多一个解析器依赖；只两条规则，手写更省且可单测 |
| 代码执行隔离 | 生成的 Python 直接在宿主进程跑 | Docker 容器 + 依赖白名单，业务库凭证根本不下发 | 模型生成的代码不可信，容器是唯一可靠的边界；`python_sandbox_enabled=False` 时跳过连续的 python 步骤，这条降级路径有 5 个用例覆盖 |

## 踩坑复盘

### 重试预算跨步泄漏：5 步计划只有第 1 步的校验生效

- **现象**：多步计划跑完看似成功，实际只有第一个查询的同比口径被纠正，后面几个照样带着 `LAG(12)` 截窗口。报告里第一个数对、后面几个数错，很难归因。
- **定位**：`sql_retry` 是普通字段，只增不减。第 1 步把 3 次额度用完，第 2 步进来时额度已经是满的，路由和校验都判「没预算」，直接降级通过——5 步计划只有 1 步真被校验（1/5）。
- **改法**：`executor` 节点每进新步就清零 `sql_error / sql_retry / python_error / python_retry / python_ok`；但 `previous_sql` 故意不清——上一句 SQL 是下一句改口径的起点。
- **结果**：多步计划校验覆盖率 20% → 100%（5/5），并补了单测锁住这个行为，防止以后又有人「优化」掉这行重置。

### 长耗时节点被空闲超时误杀

- **现象**：重查询和大结果集步骤偶发连接中断，报告生成到中途停住。
- **定位**：Reactor 的 `.timeout(45s)` 判的是「两个事件之间有没有帧」。Python 侧队列空着等模型、等执行结果时一个帧都不发，45 秒后被判成死连接。
- **改法**：超时分三层——连接 3s、空闲 45s、整次 run 600s；Python 用 `asyncio.wait_for` 在队列空转 15s 时产出一个**正式的** `event: heartbeat` 帧，Java adapter 收到后翻成 SSE 注释帧 `: ping`。
- **关键细节**：注释帧会被 `EventSource` 忽略、不进 `onmessage`，但在 Reactor 里它是一个正常的 `onNext` 元素，`.timeout()` 计时器因此重置。所以 timeout 必须套在 adapter **之前**——放之后也收得到，但那样就把「存活判定」耦合进了「协议翻译」。
- **结果**：长耗时节点误杀降为 0，同时保住首字 P95 ≤3s。

### 静默错数：SQL 跑通、报告生成，但数字是错的

- **现象**：同比数值明显偏大，个别维度整行为 0，模型自己不报任何错。
- **定位**：两类错数——窗口不足 24 个月就做同比（基期被截断）、`COALESCE(..., 0)` 把缺失基期算成 0。
- **改法**：`sql_checks.py` 两条纯函数规则（`REQUIRED_LOOKBACK_MONTHS=24` / `MIN_YOY_OFFSET=12`），零 token 成本，在结果进报告前拦截；判断窗口时取**最大**而不是最小——只要有一个分支窗口够宽，同比就成立。
- **已知漏检**：literal-date 窗口（`WHERE dt > '2024-01-01'`）不做推断，因为猜错比不猜更糟。
- **结果**：配合三层自省，SQL 一次通过率 74% → 91%（N=120 评测集）。

### 上一轮的回答冒充这一轮，用户连收两条一模一样的「没召回到表结构」

- **现象**：schema 召回到 6 张表、feasibility 补了口径、planner 也出了计划，用户收到的却是上一轮的「没有召回到可用的表结构」，而且连发两轮一模一样。
- **定位**：`final_answer` 是 thread 级累积状态，本轮没有产出时，收尾读到的是上一轮残留。
- **改法**：每轮开始用 `Overwrite` 重置 `_TURN_RESET` 那组字段（`final_answer` / `plan` / `current_step`…），收尾只读本轮自己写的 `self._final_answer`，确实没有就兜底一句「分析已结束，但没有生成有效结论」。
- **结果**：跨轮串答案消失。顺带修掉两个同源坑——`plan` 残留会让 executor 去执行已废弃的上一轮计划；`route_after_plan_validate` 靠 `final_answer` 判断「该收尾了」，残留会让计划校验失败时直接 END 而不是回 planner 重写。

## 现存局限与优化方向

这一节是我复查代码时自己列出来的，不粉饰。

### 请求幂等只停在协议层，没有落地

- **现状**：协议文档里设计了 `clientRequestId` + Redis SETNX 60 秒做请求幂等、`lastSeq` 做帧级去重，代码里一行都没有。已实现的去重是 C 通道的 nonce 防重放（`putIfAbsent`，上限 2 万），那是「同一个签名不能用两次」，不等于「同一个业务请求只跑一次」。
- **影响**：前端现在用 `EventSource`，断线是自动重连但不重发业务请求，实际触发路径很少；一旦换成客户端可重试的架构，就会出现同一次提问跑两遍、token 计两遍。
- **下一步**：先给 `POST /runs` 加幂等键，再做帧级去重，两步分开上。

### 配置项与真实生效路径不一致（两处）

- **现状一**：`heartbeat_seconds` 是死配置。`run_service.py` 里 `EventStream` 是无参构造，间隔永远取构造函数默认值 15 秒，`settings.heartbeat_seconds` 读了没人用。
- **现状二**：Java 侧 `runTimeout=30m` 只出现在启动指纹日志里。真正管住一次分析时长的是 Python 的 `asyncio.timeout(600s)`。
- **影响**：运维照 30 分钟排障会误判；想按环境调心跳只能改代码。
- **下一步**：`heartbeat_seconds` 改成 `default_factory` 把 settings 传进去，一行的事（没改是因为 15 秒对 45 秒空闲有 3 倍余量）；`runTimeout` 要么给 Flux 加 `take(Duration)` 让它真生效，要么从配置里删掉——留一个只出现在日志里的数字，比没有更糟。

### 删数据源不清向量，索引会串

- **现状**：`deleteDatasource` 只删 `agent_datasource` 关联和 `datasource` 行；清理方法 `clearSchemaDataForDatasource` 其实写好了，但全项目没有任何调用方。
- **影响**：`datasource_id` 被复用后，新数据源会继承旧库的表索引，模型拿着已经不存在的表去写 SQL。
- **下一步**：删除时同步调用清理，或改成软删除 + 异步回收，并在删除接口上补测试。

### init 是整源覆盖，不是按表增量

- **现状**：`replaceSchemaDocuments` 以 `datasourceId` 作为唯一身份，一次性替换该数据源下全部表/列文档。写库顺序是先加新文档再删旧文档，失败回滚，所以不会出现「旧的删了新的没进来」的空窗。
- **影响**：智能体 A 勾 3 张表、B 放开 10 张，谁后点「初始化」谁覆盖，共享同一份索引；不同智能体的可见表靠检索阶段按勾选过滤，而不是各存一份子集。
- **下一步**：文档身份改成 `datasourceId + agentId + 勾选范围`，支持按智能体各存一份索引。

### 进程内 run 注册表限制了横向扩容

- **现状**：取消一个 run 需要精确杀死那个协程，跨实例做不到，所以注册表放在进程内，`Dockerfile` 刻意 `--workers 1`。
- **影响**：扩容只能靠多副本 + 网关侧 `sessionAffinity`，单副本 CPU 打满时同一会话会被拖慢。
- **下一步**：把 run 句柄外置到 Redis 并加取消信号，让任意副本都能取消；短期先做副本数弹性 + sticky 路由。

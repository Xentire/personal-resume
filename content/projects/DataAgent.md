## 架构取舍对比

下面每个决策点都能对应到一条可验证的结果，不做「用了什么技术」的罗列。

| 决策点 | 备选方案 | 实际选择 | 依据与结果 |
| --- | --- | --- | --- |
| 编排范式 | ReAct：边想边调工具，步数不可预估 | Plan-and-Execute：17 节点 / 4 阶段（理解 6 · 计划 4 · 执行 6 · 交付 1） | 长链路要的是路径与成本可控，发散无法验收；先出完整计划再执行，才能给每一步挂上校验 |
| 服务边界 | 单个 Java 服务内嵌全部编排逻辑 | Java 事实层（权限 / 数据 / SQL 执行）+ Python 决策层（编排 / 推理），自定义线协议 + 7 个能力回源接口 | 权限与凭证必须留在 Java；编排用 LangGraph 更省事。重构后 Java 侧净减 60 个文件，SQL 执行入口收敛为 1 个签名校验门面 |
| 检索策略 | 纯向量召回 | 向量 + BM25 混合检索 + RRF 融合（K=60） | 表名、字段名这类精确词向量化后反而模糊，BM25 补精确匹配；TopK 命中率 61% → 79% |
| 质量兜底 | 只靠模型自省，错了再问一遍 | 三层自省（计划结构校验回退重规划 / SQL 多轮重试 / 语义层检测 SQL 与 Schema 冲突）+ 零 token 的纯函数机械校验 | 同比基期截断、缺失补零这两类错数模型自己发现不了；SQL 一次通过率 74% → 91%（N=120 评测集） |
| 人工介入 | 依赖 checkpoint 内部结构做中断恢复 | Python 侧 `interrupt` 断点 + Java 侧协议翻译与恢复 | 不把框架内部结构暴露成跨服务契约，升级 LangGraph 不会连带改 Java；执行前暂停确认、反馈后恢复或重新规划 |
| 代码执行隔离 | 生成的 Python 直接在宿主进程里跑 | Docker 容器隔离，依赖白名单由基础设施管控，与业务库凭证隔离 | 模型生成的代码不可信，容器是唯一可靠的边界；白名单放基础设施侧，业务代码拿不到执行权限 |
| 模型配置 | 各处写死模型名与参数 | 收敛成单出口，运行时热切换 | 换模型、切供应商不需要重启，也不需要改业务节点 |

## 踩坑复盘

### 重试预算跨步泄漏，多步计划只有两成步骤真被校验

- **现象**：多步计划跑完看似成功，实际只有 20% 的步骤走完了校验，其余步骤被跳过。
- **定位**：计划修复环、SQL 重试环、Python 重试环三环共用一份递归预算。靠前的步骤重试把预算吃光，后面的步骤拿不到重试额度，直接降级通过。
- **改法**：预算按步骤隔离，三环各自的递归上限统一设为 60，跨步不再共享。
- **结果**：多步计划的校验覆盖率 20% → 100%。

### 长耗时节点被心跳误杀

- **现象**：重查询和大结果集步骤偶发连接中断，报告生成到中途停住。
- **定位**：心跳超时与空闲超时共用一个阈值，且存活判定发生在协议翻译之后。长耗时步骤在等执行结果期间被判成死连接。
- **改法**：心跳与空闲超时分层，存活判定前移到协议翻译之前。
- **结果**：长耗时节点误杀降为 0，同时保住首字 P95 ≤3s。

### 静默错数：SQL 跑通、报告生成，但数字是错的

- **现象**：同比数值明显偏大，个别维度整行为 0。
- **定位**：同比基期被截断、缺失数据被补零，这两类错误在语义上都"说得通"，模型自省抓不到。
- **改法**：在结果进报告前加一层零 token 成本的纯函数机械校验，专门拦这两类。
- **结果**：配合三层自省，SQL 一次通过率 74% → 91%（N=120 评测集）。

### SQL 与 Schema 冲突时，重试丢了上下文

- **现象**：重试提示里只有一句"执行失败"，模型不知道是字段不存在、类型不匹配还是权限问题，反复改同一处。
- **定位**：错误信息被压成一句话，Schema 上下文丢失，重试实际上是盲试。
- **改法**：语义层主动检测 SQL 与 Schema 的冲突，把冲突字段与上下文一起带回修复提示。
- **结果**：重试收敛，失败样本并入 74% → 91% 的整体提升。
